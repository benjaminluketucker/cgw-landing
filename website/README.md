# Website source and adoption

COMPOSITION: Dashboard owns saved Home copy/photos and frozen release jobs. This folder is the exact executable template shared with cgw-landing/website. The Git-reviewed `adopted-template.json` is the runtime source authority; its writer is a reviewed source commit. The guard and both builders read it. Keep both Website folders byte-identical. `live-source.json` stays unchanged as genesis evidence and no longer chooses runtime acceptance.

An adoption records the previous/new oracle inventories and their SHA-256 hashes, the previous/new full template identities, exact new routing hash, reviewer, coordinator go reference and date. Oracle hashes cover `JSON.stringify(oracle, null, 2) + '\n'`. Inventories contain every template file in sorted path order. The full identity covers renderer, builder, remote transport, seed, genesis evidence, all template files and the canonical adoption bytes. Its own `newTemplateHash` field alone is replaced by 64 zeroes during hashing, avoiding self-reference. Every other adoption field is bound into the frozen job's existing `template_hash`, so a different manifest in the landing repo refuses the packet. There is no separate adoption store or API.

The template source and its adoption must land in the same reviewed commit. A candidate must match the NEW inventory and full identity exactly, including Home source, routing and the poster files. Live must match ONE complete previous or new protected inventory, never a mixture. Home output remains owned content; legal pages, AASA, open routes, assets and all other protected bytes remain checked. The original static source SHA attests routing; editor releases require the exact previousSourceCommit for the previous inventory or configured candidate SHA for the new inventory, release manifest, template identity, known output inventory and public routing readback. The guard retains no-store bounded GETs, provider credential separation, project/READY checks and alias readback. The worker's existing final protection call remains unchanged. Existing publishing permissions and release gates still apply.

Git history is the append-only adoption record. Rollback is a NEW reviewed commit with retained prior template bytes as the new oracle, the current oracle/template as previous, and a new review/go/date. Recompute the full identity for the compatible current builder, then prepare a fresh job through the normal Website workflow. Never rewrite an old packet, reset content/photos, edit an installed migration, or treat this record as activation permission.

The initial record cites the coordinator's 30 October simplified BUILD decision, not independent implementation approval or a production go. Independent review, exact-source Mac checks, current live readback, hosted open/refresh/idle measurements and real-phone acceptance remain separate release gates. This build adds no visitor code, requests or polling.

Focused guard coverage: `node --test --test-concurrency=1 editorial-dashboard/test/website-preservation.test.cjs` in cgw-app. Packet/source custody: `node --test scripts/test-article-website-template.cjs`. Run the latter again with `CGW_WEBSITE_TEST_ROOT` pointing to the landing Website folder to verify the same frozen closure. No activation, deployment or provider setting changes are implied by these commands.

R3 source acceptance runs only at Git-connected build time, through `accept-source.cjs`: the Dashboard build entrypoint and landing remote builder both call it before output/network work. Pure artifact reconstruction and request handlers do not run Git. Missing, shallow or over-64-event history, dirty Website source, source changed after the latest adoption, an absent parent, wrong parent hashes, a split source/adoption commit, a reused decision reference or an unbound transition fail closed. Git operations have a ten-second total budget and two-second per-call limit. Supply complete Git history before building; no bypass is provided.

A forward/rollback `adoption` takes the PARENT adoption's NEW oracle/template hashes and separately pins that editor artifact's exact Git source in `previousSourceCommit`. A `source-repair` keeps the parent's exact previous oracle/template/source binding and identical NEW protected inventory while changing executable source in the same commit. R3 uses this explicit mode because the preceding candidate never activated; it cannot nominate a new previous live artifact. Both modes bind the exact parent manifest hash, all source bytes, metadata and unique Linear decision-comment reference via `transitionHash`. Source review must verify the named decision's actual authority and scope. URL syntax and Git checks cannot prove human approval. The R3 reference records only the supplied source-repair direction, never production approval.

Manifests are read as Buffers and must equal canonical UTF-8 bytes exactly; executable source hashing also preserves raw bytes. Only the unchanged complete genesis oracle can use static Git routing attestation. Every editor artifact, including a previous artifact, must expose its full release manifest and routing readback. No key, endpoint, database table or visitor work was added.

R5 live-anchor selection is fixed in source: landing uses `https://coolgirlwears.app` and project `prj_yoIR8n7hVye6u96Im2gsfKTPMDcd`; Dashboard keeps its separate fixed production binding. Landing environment selectors and `env`/`build.env` selectors in `vercel.json` from the Website directory through the Git root may repeat the fixed binding but any conflict refuses before provider reads. Neither candidate configuration nor historical aliases can select live. Existing token/team credential inputs remain unchanged.
